# 个人开发工作流

## 每次开发

1. 从任务板选一个可在一次开发时段内验证的任务，同时进行的任务尽量只有一个。
2. 写清验收条件，再实现最小版本；核心玩法未验证前使用占位资源。
3. 运行受影响场景，验证目标行为、失败情况与重新开始。记录真实结果。
4. 更新任务板和必要文档，检查差异，提交一个完整变化。

## 每个迭代

- 开始：选择一个体验目标，列出本次不做的内容。按个人可用时间安排，不预设发布日期。
- 中途：尽早交给别人试玩，先观察其行为，避免提前解释操作答案。
- 结束：保存可玩的构建和版本标识，记录问题；决定保留、修改或删掉什么。

## 阶段门槛

| 阶段 | 需要回答的问题 | 结束条件 |
| --- | --- | --- |
| 核心原型 | 核心行为是否有趣？ | 能完成一次行动、反馈、失败或结束、重试，并收集试玩证据 |
| 垂直切片 | 目标品质和制作流程能否实现？ | 一个小片段包含代表性的画面、声音、交互与目标平台构建 |
| 内容制作 | 能否在预算内完成？ | 内容清单有上限，按已验证流程生产 |
| 发布准备 | 陌生玩家能否顺利玩到结束？ | 关键问题已处理，实际完成安装、首次进入、退出与重启验证 |

## 完成定义

验收条件满足；相关行为实际运行验证；没有阻塞流程的错误；外部素材有授权记录；必要操作或构建说明已更新。若无法验证，明确写明未验证原因，不能标记为已通过。

## 构建与备份

构建输出使用 `builds/<version>/<platform>/`，同时记录提交标识、引擎版本和已知问题。构建默认不进 Git，可在未来使用发行附件存档。源文件与仓库应有独立备份，并定期尝试恢复。
